# AI Test Generator

**An autonomous software test generation laboratory using Large Language Models (LLM) and Multi-Agent architecture.**  
Karate DSL · Selenium · Appium · ISTQB Standards · Self-Healing · Dark Dashboard

---

## Project Purpose and Core Capabilities

This project not only automates traditional manual test writing but also generates end-to-end tests at international **ISTQB standards** by simulating **8 different AI agents** representing various roles in the software development lifecycle (Business Analyst, Test Engineer, Security Specialist, etc.).

### Key Features

1. **Multi-Agent Architecture (8-Agent Structure):** 
   Instead of a single prompt, the system consists of 8 different expert AI agents that feed into each other.
2. **ISTQB Standards Integration:** 
   The generated tests are not simple "Happy Path" tests. The system designs negative and edge-case scenarios using engineering approaches such as Boundary Value Analysis (BVA), Equivalence Partitioning (EP), and Error Guessing.
3. **Instant Self-Healing:** 
   When a test fails (`FAILED`) due to changes in API contracts or instant errors, the system does not stop. It reads the error log (stacktrace), sends it back to the LLM, detects the error, automatically fixes the code, and re-runs it (as `_Fixed_v1`).
4. **Dark Glassmorphism Dashboard:** 
   Instead of using the system from the command line, you can manage it from a modern interface. You can trigger tests instantly by entering a Swagger URL and a User Story, and review the agents' analysis details from the report tab.

### Multi-Agent Architecture (Agent Roles)

The 8 different LLM agents in the system work sequentially, mimicking the software cycle:
* **Product Manager:** Analyzes requirements and extracts business risks and acceptance criteria.
* **Developer:** Examines the Swagger/API document from a technical perspective and determines data/constraint rules.
* **Test Analyst:** Creates a positive and negative (BVA, EP) test strategy in accordance with ISTQB rules.
* **Test Automation:** Converts analyses into executable test codes (e.g., Karate DSL).
* **Performance:** Determines SLA metrics and reports load/performance test requirements.
* **DevOps:** Designs the integration plan of tests into CI/CD (Jenkins, etc.) and Allure reporting processes. It also ensures OCP (OpenShift) compatibility.
* **SecOps:** Applies protection rules for OWASP security vulnerabilities (SQL Injection, XSS, 401/403).
* **Report:** Consolidates all data to extract the final test coverage rates and executive summary.

## LLM Model Used

By default, the **`gemma4:31b-cloud`** model is used in the project. This model, from Google's powerful Gemma 4 series, can thoroughly analyze complex Swagger files and multi-agent communications in a single pass thanks to its 256K wide context window capacity. The infrastructure is designed to easily adapt to different local models via Ollama if desired.

## Quick Start

The easiest installation method is to use the automated setup script included with the project. This script installs dependencies like Docker, PostgreSQL, MailHog, Allure, Selenium Grid, and Ollama (LLM) if missing, and starts the system with a single command.

```bash
# To install and start the entire system with a single command:
chmod +x setup.sh && ./setup.sh
```

### Manual Development Environment (Without Docker)
If you don't want to use Docker and just want to test the project with an in-memory (H2) database (requires Java 17+):
```bash
./mvnw clean install -DskipTests
./mvnw spring-boot:run -Dspring.profiles.active=local
```

### Accessing the Application Interface
Once the system is up and running, you can start using the system by navigating to the following link in your browser:
**Access Address:** http://localhost:8080

## API and Integrations

Thanks to the powerful REST API running behind the interface (Dashboard), you can integrate the system into your own CI/CD pipelines:

| Endpoint | HTTP | Description |
|----------|------|-------------|
| `/api/v1/tests/generate` | POST | Starts a new test generation request |
| `/api/v1/tests/{id}/run-all` | POST | Compiles and runs the generated tests |
| `/api/v1/tests/{id}/llm-report`| GET | Returns the detailed analyses extracted by each agent |

## How Does the Self-Healing Flow Work?

Tests triggered from the user interface or the Scheduler are checked by the `TestRunnerService` after execution. 
If a failed (`FAILED`) test is found:
1. `FailureAnalysisService` analyzes the error.
2. The corrected test scenario is generated by combining the original code and the error output (stacktrace).
3. The new scenario is executed instantly and the results are added to the final report.
